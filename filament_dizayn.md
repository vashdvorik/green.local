# UI Layout Rules для FILAMENT

## Рациональное использование пространства

При создании интерфейсов приоритетом должно быть эффективное использование доступной площади экрана. Интерфейс должен быть компактным, понятным и визуально лёгким, без чрезмерной вложенности контейнеров и пустого пространства.

### Контейнеры

* Не создавать контейнер только ради визуального оформления.
* Каждый `card`, `panel`, `section`, `wrapper` или другой контейнер должен иметь конкретную функциональную или смысловую причину существования.
* Не помещать контейнер внутрь другого контейнера, если содержимое можно расположить непосредственно в родительском элементе.
* Избегать структуры вида:
  `page → card → card → section → card → field`.
* Стремиться к максимально плоской структуре DOM и визуальной иерархии.
* Обычно достаточно 1–2 уровней визуальных контейнеров.
* Не оборачивать каждое поле формы в отдельную карточку.
* Не использовать рамку вокруг блока, если его уже достаточно отделяют отступ, заголовок или фон.
* Не использовать одновременно для одного уровня группировки рамку, фон, тень и большие отступы.

### Отступы

* Не складывать большие `padding` нескольких вложенных контейнеров.
* Если родитель уже имеет внутренний отступ, дочернему элементу не следует автоматически добавлять аналогичный отступ.
* Использовать единую шкалу отступов, например:
  `4px`, `8px`, `12px`, `16px`, `24px`, `32px`.
* `16px` считать стандартным внутренним отступом для большинства рабочих блоков.
* `24–32px` использовать только для разделения крупных самостоятельных секций.
* Не использовать большие пустые области как способ сделать интерфейс визуально чистым.
* Следить за итоговым расстоянием после сложения `margin`, `padding`, `gap` и вложенных контейнеров.
* Если между краем основной области и реальным контентом образуется 40–80px пустого пространства без функциональной причины — уменьшить вложенность или отступы.

### Вертикальное пространство

* Не растягивать интерфейс по вертикали без необходимости.
* Связанные элементы размещать близко друг к другу.
* `label`, поле, подсказка, ошибка и счётчик символов должны восприниматься как одна группа.
* Не создавать отдельную строку для небольшой служебной информации, если её можно разместить рядом с соответствующим элементом.
* Короткие настройки по возможности размещать горизонтально.
* Не превращать небольшую форму в длинную вертикальную страницу.

### Горизонтальное пространство

* Использовать доступную ширину экрана рационально.
* Не ограничивать основной рабочий контент узкой колонкой при наличии свободного пространства.
* Основная рабочая область должна занимать большую часть доступной ширины.
* Второстепенные панели должны быть существенно уже основной области.
* Не создавать широкую боковую колонку ради одного селекта или одной кнопки.
* Короткие связанные поля можно размещать в одной строке.
* Не задавать `width: 100%` элементам, которым это не требуется.
* Ширина кнопок, селектов и небольших контролов должна соответствовать их назначению.

### Формы

* Формы должны быть компактными.
* Не создавать отдельную карточку вокруг каждого поля.
* Группировать только действительно связанные параметры.
* Использовать визуальное разделение между смысловыми секциями, а не между каждым контролом.
* Кнопки действий размещать рядом с объектом, к которому они относятся.
* Небольшие действия типа `copy`, `delete`, `collapse`, `move` объединять в компактную панель действий.
* Не выделять служебным кнопкам непропорционально много пространства.

### Sidebar

* Sidebar использовать только для действительно второстепенных настроек или действий.
* Ширина sidebar должна соответствовать объёму его содержимого.
* Не делать sidebar шириной 25–30% страницы ради одного небольшого блока.
* Если настроек мало, использовать компактный блок.
* Редко используемые параметры помещать в collapsible/accordion/dropdown.
* Не держать постоянно раскрытыми настройки, с которыми пользователь взаимодействует редко.

### Карточки

* Карточка должна объединять самостоятельную смысловую сущность.
* Не использовать карточки как универсальный wrapper.
* Не создавать карточку внутри карточки без веской причины.
* Для внутренних подразделов сначала использовать:

  1. заголовок;
  2. `gap`;
  3. divider;
  4. изменение фона;
  5. и только затем дополнительную карточку.
* Не использовать сильное скругление на каждом вложенном элементе.
* Не создавать эффект «матрёшки» из рамок.

### Визуальная иерархия

* Один уровень смысловой иерархии должен иметь один основной способ визуального выделения.
* Не пытаться показать иерархию исключительно количеством рамок.
* Использовать прежде всего:

  * типографику;
  * размер заголовков;
  * отступы;
  * выравнивание;
  * группировку.
* Рамки и фон использовать только там, где они действительно помогают понять структуру.

### Рабочие интерфейсы и админки

* В административных интерфейсах отдавать приоритет плотности полезной информации.
* Основной редактор, таблица, форма или рабочая область должны быть главным визуальным элементом страницы.
* Служебный UI не должен занимать больше места, чем содержимое, с которым работает пользователь.
* Пользователь должен видеть как можно больше полезного контента без постоянного скролла.
* Не жертвовать рабочей площадью ради декоративного whitespace.

### Проверка перед завершением UI

Перед завершением страницы проверить:

* Можно ли удалить хотя бы один wrapper?
* Есть ли карточки внутри карточек без функциональной необходимости?
* Не складываются ли несколько `padding` подряд?
* Есть ли большие пустые зоны?
* Можно ли объединить связанные элементы в одну строку?
* Не слишком ли широк sidebar?
* Не слишком ли узка основная рабочая область?
* Не занимают ли служебные элементы слишком много места?
* Можно ли заменить рамку простым `gap` или заголовком?
* Видно ли пользователю достаточно полезного контента без скролла?

Если элемент можно удалить без потери структуры, читаемости или функциональности — удалить его.

## Главный принцип

> Минимум контейнеров, минимум уровней вложенности, минимум лишних отступов. Максимум полезной площади экрана.

Сначала создавать максимально простой и плоский layout. Добавлять дополнительные контейнеры, рамки, панели и отступы только тогда, когда они решают конкретную UX-задачу.
